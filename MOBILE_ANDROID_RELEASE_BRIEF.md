# IziCard Manager — comparaison et cahier de livraison Android

Date : 2026-10-27. Dépôts examinés en lecture statique : `Izicard-Managers` (Flutter Android) et `izicard-managers-web` (Web/PWA/Worker). Ce document sert de référence de travail pour la suite et de prompt d’exécution à l’agent IA.

## Nom retenu

Nom produit proposé pour l’application mobile : **IziCard Manager**. Sous-titre descriptif : **Gestion et encodage NFC**. Le dépôt est nommé `Izicard-Managers`; le nom Flutter interne `izicard_nfc_app` est un identifiant technique, pas le nom à afficher. L’identifiant Android recommandé, à confirmer avant publication, est `com.izicardouaga.izicardmanager`. Ne jamais changer l’identifiant après première publication sans décision explicite.

Le projet Web est l’espace de gestion NFC IziCard. Les deux interfaces — Web et mobile — sont des clients du même produit et du même backend NFC; ce ne sont pas deux bases métier séparées.

## Comparaison rapide Web / mobile

### Fonctions métier communes déjà présentes dans les sources

Les deux clients implémentent l’authentification par email/mot de passe et la récupération par code de huit chiffres. Ils chargent le profil et le rôle depuis `nfc.nfc_profiles`, utilisent les données du schéma `nfc`, gèrent les clients et les accès, créent et suivent des dossiers, chargent les formats, importent CSV/XLS/XLSX avec correspondance de colonnes, proposent une saisie manuelle, exportent en CSV et utilisent les opérations NFC communes côté serveur.

Les principales opérations et objets communs relevés sont `nfc_create_batch`, `nfc_import_rows`, `nfc_mark_written`, `nfc_set_access`, `nfc_clients`, `nfc_batches`, `nfc_tags` et `nfc_card_formats`. Les deux clients respectent le modèle d’autorisation par RLS/RPC, sous réserve de vérifier les droits et migrations réels en environnement Supabase.

### Différences relevées

Le mobile ajoute un cache SQLite cloisonné par utilisateur, une file de synchronisation et un fonctionnement hors ligne pour les dossiers téléchargés, le détail des cartes et les écritures en attente. Il ajoute l’écriture d’une seule carte, l’aide quand NFC est désactivé, les réglages locaux, un tableau de bord Admin, l’écoute Realtime des dossiers et l’archivage/historique d’audit via `nfc_archive_batch` et `nfc_list_audit`.

Le Web couvre le parcours d’activation du mot de passe après invitation et emploie Web NFC sous Chrome Android/HTTPS. Le mobile utilise NFC natif Android. Aucune interface Web d’archivage/historique équivalente n’a été repérée. Des pages et routes Worker annoncées par les documents Web sont présentes sous forme de fichiers mais les appels métier correspondants ne sont pas tous raccordés dans `src/index.ts`; la source vérifiée indique que plusieurs opérations utilisent Supabase directement depuis les clients.

### État de vérification

La comparaison établit la présence des écrans et appels dans le code, pas leur fonctionnement en production. L’application mobile n’a ni plateforme Android complète, ni build/analyse confirmés; les quatre fichiers de test ne contiennent que des commentaires. Les migrations Supabase, les fonctions RPC, les politiques RLS, les emails réels et les opérations NFC sur appareils/tags physiques exigent une validation séparée.

Les documents du dépôt ne sont pas tous synchronisés avec le code : le registre `RESTE_A_FAIRE_MOBILE.md` est antérieur aux lots M6–M9 et décrit encore plusieurs fonctions ajoutées depuis. Pour les décisions, consulter les derniers commits, le code et les nouvelles entrées datées de `PROJECT_PROGRESS.md`.

## Consigne de sécurité et périmètre

Toute migration ou fonction créée pour cette livraison doit concerner exclusivement le schéma PostgreSQL `nfc` et l’authentification d’accès des utilisateurs de l’espace Managers. Ne pas modifier les tables, colonnes, triggers, vues, politiques, fonctions, Edge Functions, données, écrans ou flux de vente d’IziCard. Ne pas modifier les fonctions Edge déjà déployées. Ne pas toucher aux autres schémas, notamment `public`, ou aux produits et workflows IziCard sans lien avec l’encodage NFC.

Le seul projet Supabase cible est **IziCard**, référence `thsedbhzhonemdhbndpf`. La base est partagée avec le site et le portail d’administration : toute opération doit donc être circonscrite, relue et journalisée avant exécution. Ne jamais mettre `service_role`, clé Management API, secret SMTP/Resend ou autre secret serveur dans Flutter, le Web, le dépôt ou un fichier livré.

Une Edge Function `send-activation-emails` est déjà déployée. Elle est extérieure à l’authentification des clients NFC et ne doit être ni modifiée ni redéployée. L’Edge Function distincte `create-client-user` est dans le dépôt Web et est appelée par les interfaces, mais elle ne figurait pas dans la liste des Edge Functions déployées au moment de l’inspection. Créer ou déployer une fonction dédiée à l’invitation seulement après comparaison exacte du code et vérification des secrets/URL requis; ne jamais remplacer une fonction de même nom sans sauvegarde et autorisation ciblée.

## Éléments de configuration à contrôler

1. Vérifier les migrations NFC `003_nfc_enum_code`, `004_nfc_formats_rules`, `005_nfc_realtime` et `006_nfc_archive_history`, dans l’ordre de dépendance indiqué dans les fichiers, avec vérification avant/après. `001_nfc.sql` est un ancien bootstrap en `public` : ne pas le rejouer, le modifier ni l’utiliser pour reconstruire la base.
2. Vérifier les objets, valeurs enum, colonnes, RPC, grants, RLS et exposition PostgREST/Realtime uniquement dans `nfc`. Les règles métier d’accès restent côté serveur.
3. Pour les emails Auth d’invitation et de récupération : garder les flows Supabase Auth existants, valider le modèle Recovery avec `{{ .Token }}` sur huit chiffres, les URLs de redirection/d’activation, et SMTP Resend seulement si le propriétaire fournit/autorise les identifiants requis. Ne jamais inventer de clé ou afficher une valeur secrète dans un journal.
4. Ajouter/valider les liens profonds Android correspondant exactement au domaine de redirection Supabase et à l’écran d’activation, avec vérification du domaine/app links et fallback Web. Les URLs ne doivent pas pointer vers un autre produit ou schéma.
5. Ne pas déclencher d’invitation ou d’email de test vers une vraie adresse sans adresse de test explicitement fournie.
